동시에 10명이 로그인하자 전부 실패했다

로그인 서버 · 2026.08

문제 발생

구글 로그인 기능을 다 만들고 검사만 남은 날이었습니다. 동시에 5명이 로그인할 때는 문제가 없었는데, 10명이 되자 한 명도 성공하지 못했습니다.

10명 모두 30초를 기다리다 실패했고, 로그인 처리 후 지워졌어야 할 임시 데이터가 20건 남았습니다. 요청 10건에 임시 데이터가 20건이라는 점이 첫 단서였습니다.

응답이 전부 30초 근처인 것은 느려서가 아니라, DB 연결을 기다리다 정해진 대기 시간을 다 채우고 포기한 값입니다.

원인 분석

로그인이 끝난 뒤 임시 데이터를 지우는 뒷정리 작업이 같은 요청 안에서 실행되고 있었습니다. 이 뒷정리는 새 트랜잭션으로 도는데, 그러려면 DB 연결이 하나 더 필요합니다.

즉 요청 하나가 연결을 두 개씩 쥡니다. 앞 연결을 놓지 않은 채 뒤 연결을 기다리므로, 모두가 서로를 기다리는 상태가 됩니다.

가설

이 분석이 맞다면 확인 가능한 예측이 하나 나옵니다.

DB 연결을 10개까지만 쓰도록 설정해 뒀으므로, 정확히 10명째부터 무너져야 한다. 10명이 각자 하나씩 쥐면 남는 연결이 0이 되기 때문입니다. 9명까지는 여유 연결이 남아 정상 동작해야 합니다.

동시 접속을 5·10·15·20·25명으로 올리며 확인했습니다. 예측대로 5명은 정상, 10명부터 전멸이었고, 대기 중인 요청 수도 동시 접속 수와 정확히 같았습니다. 하나라도 연결을 놓았다면 그보다 적어야 합니다.

문제 해결

뒷정리 작업을 요청 처리에서 떼어내 전용 스레드로 옮겼습니다. 로그인 응답은 첫 연결만 쓰고 바로 반환되고, 뒷정리는 나중에 자기 연결을 받아 실행됩니다.

테스트 코드 안에서 잰 시간에는 네트워크와 서버 처리가 빠져 있어, 실제 HTTP 요청을 보내는 부하 도구로 가상 사용자 50명·90초 조건에서 다시 확인했습니다.

회고

평균에 가까운 지표만 보면 방향을 반대로 읽습니다. 상위 95%·99% 응답 시간은 고치기 전이 오히려 더 좋게 나왔습니다. 실패한 요청은 응답 시간 통계에 포함되지 않기 때문입니다. 그 뒤로는 응답 시간·최댓값·오류 건수를 반드시 함께 봅니다.

고치기 전 코드가 저장소에 남아 있지 않았습니다. 만드는 도중 발견해 바로 고쳤기 때문입니다. 비교 수치를 만들기 위해 저장소 사본을 따로 떼어 그 부분만 되돌린 뒤 측정했습니다.

오류 메시지 없이 채팅 15건이 사라졌다

채팅 수집 서버 · 2026.08

문제 발생

실제 방송에서 채팅을 받던 연결이 갑자기 끊겼습니다. 예외도, 종료 신호도, 오류 로그도 없었습니다. 수집된 채팅 수를 방송 화면과 대조하고 나서야 15건이 비어 있는 것을 알았습니다.

기록을 되짚어 보니 서버에 살아 있다고 알리는 신호를 74초 동안 한 번도 보내지 않은 구간이 있었고, 사라진 채팅이 정확히 그 구간의 것이었습니다.

더 나쁜 조건이 있었습니다. 재미있는 장면이 나와 채팅이 몰리는 순간에만 발생하고, 한가할 때는 멀쩡했습니다. 이 서비스가 채팅을 가장 필요로 하는 순간이 바로 그때입니다.

원인 분석

연결을 유지하려면 일정 시간마다 서버에 신호를 보내야 하고, 보내지 않으면 서버가 연결을 끊습니다. 그런데 이 신호를 채팅을 받는 자리에서 함께 보내고 있었습니다.

채팅이 몰리면 받은 것을 처리하느라 신호 보낼 차례가 오지 않습니다. 서버는 응답이 없는 연결로 판단해 조용히 끊고, 끊긴 뒤 도착한 채팅은 그대로 사라집니다. 양쪽 모두 오류를 남기지 않기 때문에 아무도 알아채지 못합니다.

가설

원인이 채팅의 양이 아니라 처리 지연이라면, 채팅을 적게 보내면서 처리만 느리게 해도 같은 현상이 나와야 합니다.

실제 방송을 기다려서는 재현할 수 없으므로 가짜 방송 서버를 만들고 채팅 처리에 일부러 지연을 넣어 확인했습니다. 예상대로 신호 간격이 늘어났고, 지연을 키우면 연결이 끊겼습니다.

기존 라이브러리를 쓰는 방법도 검토했지만 신호를 원하는 시점에 보낼 수 없는 구조여서 쓰지 않았습니다. 내부를 우회하면 라이브러리 버전이 바뀔 때 조용히 깨지는데, 신호 미전송도 조용한 고장이라 두 가지 조용한 고장이 겹치면 원인을 찾을 수 없다고 판단했습니다.

문제 해결
  • 신호를 보내는 담당을 채팅 처리와 분리했습니다. 채팅이 아무리 몰려도 신호는 제때 나갑니다.
  • 연결 유지 시간을 코드에 적어 두지 않고 상대 서버가 알려 준 값에서 계산합니다. 상대가 정책을 바꾸면 적어 둔 쪽은 조용히 어긋납니다.
  • 문제가 생기면 서버를 종료하지 않고 수집만 멈춘 뒤 상태를 이상으로 표시합니다. 종료시키면 만료된 인증 정보처럼 재시작으로 풀리지 않는 원인에서 재시작만 반복합니다.
  • 30초마다 받은 건수·신호 간격·순서 어긋남을 요약해 남깁니다. 채팅 내용 자체는 로그에 남기지 않습니다.

저장 속도를 13배 올리고, 1.7배 더 빠른 방법은 쓰지 않았다

채팅 적재 · 2026.08

문제 발생

채팅을 저장하는 작업은 한 번에 하나씩만 처리됩니다. 여기서 밀리면 채팅을 받는 쪽까지 순서대로 밀립니다.

채팅을 한 건씩 따로 저장하고 있었고, 5,000건에 0.83초가 걸렸습니다. 채팅이 몰리는 순간이 곧 저장이 가장 바쁜 순간이라, 이 상태로는 몰리는 구간에서 밀립니다.

개선 전 측정 · PostgreSQL 17 · 조건당 3회 중앙값
저장 방식5,000건 소요초당 처리
한 건씩 저장833ms6,002건
원인 분석

느린 이유가 저장 자체인지 왕복 횟수인지 갈라야 했습니다. 한 건 저장에 드는 시간에 건수를 곱한 값이 전체 시간과 거의 같았고, 병목은 DB를 5,000번 왕복하는 것이었습니다.

가설

묶어서 한 번에 보내면 왕복 횟수에 비례해 줄어든다. 다만 묶으면 어느 건이 실패했는지 알기 어려워지는 문제가 따라옵니다.

그래서 조건을 하나 걸었습니다. 속도를 올리되, 어떤 채팅이 저장되고 어떤 것이 실패했는지는 계속 알 수 있어야 한다. 이 서비스는 받은 개수 = 저장된 개수 + 중복 + 버린 개수가 맞는지 매번 확인하기 때문입니다.

문제 해결

묶음 저장으로 바꾸고, 실패한 묶음만 한 건씩 다시 넣어 원인이 된 건을 찾아내도록 했습니다. 정상 구간은 묶음 속도를 그대로 쓰고, 실패했을 때만 느린 경로로 내려갑니다.
